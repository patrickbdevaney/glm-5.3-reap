# IQ3_M MTP teacher capture — what it was, what it showed, why the bulk was deleted

**Captured** 2026-09-01. **Hidden states deleted** 2026-09-06 after the analysis below.
The corpus (token ids + sequence lengths) is preserved here; the 163.8 GB of hidden states is not.

## What was captured

Final hidden states of **GLM-5.3-Flash-REAP50 at IQ3_M**, one fp16 4096-vector per token, via
`llama-embedding --pooling none` — which is exactly the MTP block's `h_prev` input (verified
against vLLM: `Glm4MoeModel.forward` returns the post-final-norm tensor, and llama.cpp's
`res->t_embd` is set from the same point in `src/models/glm5-next.cpp`, so no rescale is needed).

| | |
|---|---|
| chunks | 80 (`chunk_0000.bin` … ) |
| tokens | **19,999,069** |
| sequences | 14,160 |
| hidden states | 163.8 GB, fp16, 8192 B/token — **deleted** |
| corpus (`*.ids`, `*.lens`) | 77 MB — **kept, in `corpus/`** |

The capture was **complete and internally consistent**: every chunk's `lens` sums exactly to the
token count implied by its file size, across all 80 chunks, and the preserved ids re-verify at
19,999,069 against the same lens. It did not fail. It was never trained on.

## Why it was deleted rather than used

Three independent findings, each sufficient on its own. None of them is a defect in the capture.

**1. It cannot serve the NVFP4 engine, which is the target that matters.** Final hidden states
drift hard across quantizations — measured, not assumed, on 26,364 matched tokens with identical
token ids:

| pair | cosine mean | p50 | rows <0.95 |
|---|---|---|---|
| NVFP4 vs IQ3_M | 0.901 | 0.916 | 95.8% |
| NVFP4 vs IQ4_XS | 0.928 | 0.943 | 60.4% |
| IQ3_M vs IQ4_XS | 0.891 | 0.906 | 98.3% |
| **IQ3_M vs IQ3_M (control)** | **0.99892** | 1.0 | 0.4% |

Against a 0.999 same-quant floor, ~0.90 is a real train/serve distribution shift. A head trained
on these states is an IQ3_M head and nothing else.

**2. An IQ3_M head could not have paid off anyway.** With the *native, un-fine-tuned* `blk.45`,
speculation already reaches 46.5% acceptance at depth 2 and 58.5% at depth 3 — and is still a
**net slowdown**: IQ3_M at `-ngl 24` goes 2.99 t/s baseline → 1.73 (depth 2) → 1.85 (depth 3).
The draft costs 5.3 ms/token against a 334 ms decode. The loss is entirely that llama.cpp's
partially-offloaded target gains almost nothing from batching below 32 tokens
(`op_offload_min_batch_size = 32`), which is exactly the width range speculation needs. A better
head does not move that.

**3. Nothing was trained, so there is no model to preserve.** Every acceptance number ever
measured for this project came from the stock MTP block.

## What was kept, and why that is the valuable part

`corpus/*.ids` and `corpus/*.lens` — the exact 19,999,069-token, 14,160-sequence corpus, in
capture order. **Token ids are quantization-independent.** Re-running the capture against any
other quantization with these ids reproduces a matched dataset, which is what makes a
cross-quant comparison exact rather than approximate (this is how the 0.999 same-quant control
above was possible at all). The expensive, non-reproducible part of the capture was corpus
selection and bucketing; the hidden states are a deterministic function of (corpus, checkpoint)
and can be regenerated by `scripts/nvfp4_trace_capture.py` or `llama-embedding --pooling none`.

Kept locally rather than published: 20M tokens of ids are a reconstructable corpus, and
redistributing it is a licensing question that publishing a dataset card is not.

## The honest summary

A 163.8 GB capture, technically flawless, aimed at a target that measurement later showed could
not win. The finding that killed it — that hidden states drift ~0.90 across quantizations against
a 0.999 floor — is itself a durable, transferable result, and it was produced by this work.
The lesson to carry: **measure the serving-side batching curve before capturing a training set
for a draft head**, because the head is not usually the bottleneck.
