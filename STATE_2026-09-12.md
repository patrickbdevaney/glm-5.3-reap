## OPEN: the splice is not exact, and I said it was

`eval_humaneval.py --only-truncated-in` was justified by "greedy decoding means max_tokens can
only STOP a sequence, never steer one, so carried rows are bit-identical." The pilot falsified
that: HumanEval/21 and /22 finished at 3742 and 2611 tokens -- BELOW the old 4096 cap -- yet both
had truncated at 4096. Same prompt, same effort, greedy.

`max_tokens` is not the cause; the server does not template it into the prompt (checked
server/server.cpp, include/openai_api.h). The suspect is `--seqmax`, raised 8192 -> 20480 for the
pilot, which resizes the attention arena and chunk schedule and so changes reduction order. The
gate ran both binaries at the SAME seqmax, which is why it came out bit-identical and did not
catch this.

**First thing on resume**, before any more eval GPU hours: re-run HumanEval/21 and /22 at
`--seqmax 20480 --max-tokens 4096`. If they complete at 3742 / 2611 there, seqmax is the cause,
splicing stays usable, and STAGE B must hold seqmax FIXED across every arm it compares. If they
truncate instead, max_tokens does steer this engine and the splice is unusable -- STAGE B becomes
a full 164-problem re-run per arm.
